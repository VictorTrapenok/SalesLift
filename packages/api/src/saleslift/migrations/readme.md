# Миграции

Alembic поверх async-движка. Целевая СУБД — PostgreSQL 18.

## Команды

```bash
make dev                                    # поднимет БД, если ещё не поднята

cd packages/api
DB_HOST=localhost uv run alembic upgrade head          # накатить
DB_HOST=localhost uv run alembic downgrade -1          # откатить одну
DB_HOST=localhost uv run alembic current               # текущая ревизия
DB_HOST=localhost uv run alembic check                 # расходятся ли модели со схемой
DB_HOST=localhost uv run alembic revision --autogenerate -m "описание" --rev-id 0002
```

В контейнере миграции накатывает отдельный одноразовый сервис `migrate`
(docker compose) или initContainer (k8s) — но **никогда не оба сразу**.

## Правила

### Autogenerate даёт черновик, а не результат

Каждую сгенерированную миграцию **читать глазами**. Alembic хорошо видит
таблицы, колонки, внешние ключи и (в нашей конфигурации) частичные индексы с
CHECK-ограничениями, но не гарантирует этого. Отдельно проверять:
`server_default=text(...)`, изменения типов, всё, что связано с данными.

Миграции данных autogenerate не пишет вообще — только структуру.

### `op.*` по умолчанию, сырой SQL — по необходимости

Правило прототипа «только сырой SQL, один statement на вызов» существовало
из-за неудобства `queryInterface` в Sequelize. В Alembic операции `op.*`
выражают всё, что нам нужно, **и дают обратимый `downgrade()`**. Опускаться до
`op.execute("...")` — только там, где операции не хватает.

### Без префикса схемы

В SQL миграций не должно быть `public.` и любых других префиксов схемы. Схема
определяется `search_path` соединения, а не текстом запроса. Правило перенесено
из прототипа дословно, потому что оно по-прежнему верно.

### Именование ревизий

Номера последовательные, задаются явно: `--rev-id 0002`. Имя файла —
`0002_короткое_описание.py` (шаблон `file_template` в `alembic.ini`). Порядок
миграций должен читаться в имени файла, а не выясняться раскруткой цепочки
`down_revision`.

### `downgrade()` обязателен и должен работать

Проверка не «код написан», а «прогнан»:

```bash
uv run alembic upgrade head && uv run alembic downgrade base && uv run alembic upgrade head
```

## URL берётся из settings

`env.py` подставляет `settings.database_url` поверх плейсхолдера из
`alembic.ini`. Значение `sqlalchemy.url` в `alembic.ini` не используется — оно
там только чтобы Alembic не ругался на отсутствие ключа. Конфигурация БД
должна быть в одном месте, иначе приложение и миграции однажды поедут в разные
базы.

Синхронный драйвер не нужен: `env.py` работает через
`connection.run_sync(...)` поверх async-соединения. Поэтому в зависимостях нет
`psycopg2` — только `asyncpg`.

## Совместимость при выкатке — expand-contract

**Это самое вероятное место production-инцидента, читайте внимательно.**

В кластере под с новым образом приезжает, пока старые поды ещё живы
(`maxUnavailable: 0`), а миграция накатывается pre-upgrade хуком **до** них.
Значит, схема после миграции обязана быть совместима с **предыдущей** версией
кода — хотя бы на один релиз.

Практически это означает: не удалять и не переименовывать колонки за один шаг.

| Шаг | Релиз N              | Релиз N+1                          |
| --- | -------------------- | ---------------------------------- |
| 1   | Добавить новую колонку (nullable) | —                     |
| 2   | Писать в обе колонки | —                                  |
| 3   | —                    | Читать из новой, удалить старую    |

Подробности про выкатку — в [deploy/README.md](../../../../deploy/README.md).
