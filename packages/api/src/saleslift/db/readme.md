# Слой базы данных

SQLAlchemy 2.0 (async) + asyncpg + PostgreSQL 18. Миграции — Alembic, см.
[migrations/readme.md](../migrations/readme.md).

## Состав

| Файл             | Назначение                                                     |
| ---------------- | -------------------------------------------------------------- |
| `base.py`        | `Base` + миксины `UuidPkMixin`, `TimestampMixin`, `SoftDeleteMixin` |
| `session.py`     | Движок и фабрика сессий                                         |
| `soft_delete.py` | Глобальный фильтр мягко удалённых записей                      |

## Соглашения по таблицам

У каждой таблицы: UUIDv4 PK (генерируется базой), `created_at`/`updated_at`,
мягкое удаление через `deleted_at`. Достигается наследованием:

```python
class Tenant(UuidPkMixin, TimestampMixin, SoftDeleteMixin, Base):
    __tablename__ = "tenants"
```

Порядок колонок в DDL задаётся `sort_order`: `id` идёт первым (-100),
служебные отметки времени — последними (100–102). Без этого колонки миксинов
уезжают в конец таблицы и `\d` читается хуже.

### Про `underscored: true`

В прототипе на Sequelize эта опция включалась у каждой модели, чтобы
camelCase-атрибуты отображались в snake_case-колонки. Здесь она не нужна и её
аналога нет: атрибуты Python и так snake_case. Не пытайтесь её «вернуть» —
искать нечего.

## Мягкое удаление — невидимая магия

`soft_delete.py` вешает слушателя на `do_orm_execute`, который добавляет
`WHERE deleted_at IS NULL` **в каждый ORM-SELECT** по модели с
`SoftDeleteMixin`. Это аналог `paranoid: true` из Sequelize и единственный
паттерн прототипа, у которого в SQLAlchemy нет встроенного соответствия.

Фильтр применяется и к eager-подгруженным связям (`include_aliases=True`):
`selectinload(Tenant.users)` тоже не вернёт удалённых.

**Как получить удалённые записи** (админские отчёты, восстановление):

```python
from saleslift.db.soft_delete import include_deleted

stmt = select(User).execution_options(**include_deleted())
```

Побочный эффект, о котором стоит помнить: строка удалённого сотрудника
физически остаётся в таблице. Именно поэтому уникальный индекс по `email`
частичный (`WHERE deleted_at IS NULL`) — иначе адрес уволенного сотрудника
навсегда остался бы занятым.

## Мультитенантность делается НЕ здесь

Соблазнительно повесить на `do_orm_execute` второй критерий, подставляющий
`tenant_id` из contextvar, и получить изоляцию «бесплатно». **Не делайте
этого.** Фоновые задачи легитимно ходят между тенантами, и фильтр, который в
одном пути кода молча применяется, а в другом нет, опаснее отсутствия фильтра:
он создаёт ложное чувство защищённости.

Дисциплина вместо магии: каждый метод сервиса принимает `tenant_id` явным
аргументом, каждый запрос содержит явный `.where(Model.tenant_id == tenant_id)`.
Гарантия — интеграционные тесты: у каждого tenant-scoped сервиса обязателен
кейс «не видит данные чужого тенанта» (фикстура `other_tenant`).

Postgres RLS — возможный будущий слой усиления поверх этой дисциплины, но не
замена ей.

## Сессия — первым аргументом сервиса

`AsyncSession` не безопасна при конкурентном использовании, поэтому она не
может быть модульным глобалом, каким было соединение Sequelize в прототипе.
Сессия создаётся на запрос и передаётся явно:

```python
await auth_service.register(session, input, locale)
```

Отвергнутая альтернатива — `async_scoped_session` с contextvar: сохранила бы
сигнатуру прототипа, но прячет сессию, усложняет тесты и ломается в фоновых
задачах, где никакого запроса нет.

Транзакциями управляет сервисный слой (`async with session.begin():`), а не
резолвер: граница транзакции — это бизнес-решение («тенант и админ создаются
вместе или не создаются вовсе»), а не деталь транспорта.
