# Роли и разрешения

## Устройство

Три файла с чётко разделёнными ролями:

| Файл                        | Что содержит                                        |
| --------------------------- | --------------------------------------------------- |
| `services/permissions.py`   | **Только** enum `UserPermissions`. Без импортов и логики. |
| `user_roles_permission.py`  | Маппинг ролей → права, гарды резолверов             |
| `graphql/types/user.py`     | Регистрация enum в GraphQL-схеме                    |

`permissions.py` держится пустым намеренно: он единственный источник истины, и
чем меньше в нём поводов для изменений, тем лучше.

## Как право попадает на фронтенд

**Через GraphQL-схему, а не копированием файла.**

```
services/permissions.py  →  strawberry.enum(...)  →  schema.graphql
                                                          ↓
                                              npm run codegen
                                                          ↓
                              generated/graphql.ts:  export enum UserPermissions
```

Прототип побайтово копировал `permissions.ts` на фронтенд шагом `cp` внутри
codegen. Между Python и TypeScript так нельзя — но писать генератор и не нужно:
в проекте уже есть кросс-языковой конвейер типов, и право едет по нему.

**Рассинхрон невозможен by construction**, а не «проверяется»: удалите значение,
на которое ссылается фронтенд, и `npm run codegen` упадёт на стейдже
`web-builder` — тем же механизмом, что и переименование любого другого поля.
Битый образ не соберётся и не уедет в registry.

В `codegen.ts` стоит `namingConvention: { enumValues: 'keep' }`. Без него
codegen переименовал бы `Permission_users_see` → `PermissionUsersSee`, и одно и
то же право звалось бы по-разному в двух языках — грепом такую пару не найти.

## Массив `users.permissions`

Содержит **маркер роли** (`admin` / `manager` / `viewer`) и опционально
значения `UserPermissions`, точечно расширяющие роль:

```json
["viewer", "Permission_org_settings_see"]
```

⚠️ **Порядок записей значения не несёт.** Искать роль по `permissions[0]`
нельзя. Читать права **только** через `get_effective_permissions()`.

Неизвестные значения игнорируются: выкатка, удаляющая право, не должна ронять
вход пользователям, у которых оно ещё записано в БД.

## Гарды

```python
require_auth(ctx)                              # просто аутентифицирован
require_permission(ctx, UserPermissions.X)     # есть конкретное право
require_admin(ctx)                             # администратор компании
```

Все возвращают `AuthenticatedContext` — сужённый dataclass, где `user` и
`tenant` не `None`. Это не косметика: mypy тогда **доказывает**, что защищённый
резолвер не обратится к `None`-пользователю, а забытый гард становится ошибкой
типов, а не багом в production.

```python
@strawberry.field
async def resolver_users_list(self, info: Info[Context, None]) -> list[User]:
    auth = require_permission(info.context, UserPermissions.Permission_users_see)
    return await users_service.list_employees(info.context.session, auth.tenant_id)
```

Гард бросает доменную ошибку; локализует её расширение схемы
`DomainErrorExtension` — оборачивать резолвер в `try/except` не нужно.

## Гейтинг UI — только следствие

`HasPermission` и проверки на фронтенде **не защищают данные**. Скрытая кнопка
— это вежливость к пользователю, а не безопасность. Настоящая проверка всегда в
резолвере.

Правило: **на каждое `HasPermission` на фронтенде должен быть
`require_permission` в соответствующем резолвере.**

## Добавление права

1. Значение в enum в `services/permissions.py`.
2. Прописать в `USERS_ROLE_MAP` в этом же каталоге — иначе право не попадёт
   никому.
3. Использовать в резолвере: `require_permission(ctx, UserPermissions.X)`.
4. `make codegen` — enum на фронтенде обновится сам.

`tests/unit/test_permissions.py` проверит, что `USERS_ROLE_MAP` не ссылается на
несуществующие права.

## Текущие роли

| Роль      | Права                                                          |
| --------- | -------------------------------------------------------------- |
| `admin`   | Все                                                            |
| `manager` | Видеть сотрудников, видеть настройки компании                   |
| `viewer`  | Видеть сотрудников                                             |

Управление сотрудниками (`Permission_users_edit` — смена роли и
отключение/включение, `Permission_users_delete` — удаление) есть только у
администратора. На этом же держится инвариант «последнего администратора не
разжаловать и не удалить»: действие над собой запрещено, а сделать его над
чужой учётной записью может лишь другой администратор, который после операции
остаётся. Подробнее — в docstring `UsersService._get_own_employee`.

Различаются пока только `admin` и остальные: двух страниц недостаточно, чтобы
осмысленно разграничить `manager` и `viewer`. Придумывать разграничение под
несуществующие фичи — гадание; набор расширяется по мере появления реальных
действий.

Регистрация создаёт администратора: у компании должен быть кто-то, способный
завести остальных.
