# Модели данных

Общие соглашения по таблицам (PK, отметки времени, мягкое удаление) — в
[db/readme.md](../db/readme.md).

## Реестр моделей — явный

`models/__init__.py` импортирует каждую модель поимённо. Автозагрузчика по
маске файлов нет намеренно, и от этого списка зависят две вещи:

- `Base.metadata` знает обо всех таблицах, поэтому `alembic revision
  --autogenerate` видит их все;
- маппер SQLAlchemy резолвит строковые ссылки в `relationship("User")`.

**Забыли добавить импорт** — модель будет работать в рантайме, но молча
отсутствовать в autogenerate, и миграция под неё никогда не появится.

## Ключевые решения

### У тенанта нет slug

Единственный идентификатор компании — `id` (UUID). В прототипе `slug` нужен был
для поддомена `<slug>.example.com`; здесь все кабинеты живут на одном домене без
поддоменов, поэтому slug не нужен. Следствия: названия компаний **не обязаны
быть уникальными**, в форме регистрации нет поля «придумайте slug», префиксы
ключей файлового хранилища строятся по `tenant_id`.

Цена: в логах и ключах S3 стоит UUID, а не читаемое имя — чтобы понять, чья
это компания, нужен запрос в БД.

### E-mail глобально уникален

Частичный уникальный индекс `uq_users_email` (`WHERE deleted_at IS NULL`) —
это схемное выражение решения о резолвинге тенанта: форма логина содержит
только e-mail и пароль, а компания выводится из найденной строки пользователя.

**Цена решения:** один человек не может работать в двух компаниях под одним
адресом. Сознательный размен ради простоты входа.

**Контракт нормализации.** Индекс построен по обычной колонке, а не по
`lower(email)` — так `WHERE email = :email` использует индекс без обязанности
всех вызывающих оборачивать значение в `lower()`. Но это работает, только пока
в колонке лежит нормализованное значение. Две линии защиты:

1. сервисный слой нормализует e-mail перед каждой записью и каждым поиском;
2. `@validates("email")` на модели нормализует любое присваивание.

Подробности — в [services/auth/readme.md](../services/auth/readme.md).

### `users.permissions` — массив, а не колонка роли

Содержит маркер роли (`admin`/`manager`/`viewer`) и опционально значения
`UserPermissions`, точечно расширяющие роль. **Порядок значения не несёт** —
искать роль по `permissions[0]` нельзя. Читать только через
`get_effective_permissions()`, см.
[services/users/user_roles_permission.md](../services/users/user_roles_permission.md).

### `background_tasks` — очередь и трекер одновременно

В прототипе эта таблица только отображала прогресс, а очередью служила
отдельная (`incoming_events_log`). Здесь таблица одна, поэтому у неё есть
`payload` с входными данными обработчика. Подробности про захват задач —
[services/tasks/readme.md](../services/tasks/readme.md).

## Как добавить модель

1. Создать `models/<entity>.py`, унаследовать нужные миксины из `db/base.py`.
2. **Добавить импорт в `models/__init__.py`** и в `__all__`.
3. Имена ограничений задавать без префикса таблицы: его подставит
   `naming_convention` из `db/base.py`. `name="status"` → `ck_users_status`;
   `name="users_status"` дало бы `ck_users_users_status`.
4. `uv run alembic revision --autogenerate -m "..."` — это **черновик**,
   просмотреть руками (см. [migrations/readme.md](../migrations/readme.md)).
5. Прогнать `alembic upgrade head` → `downgrade base` → `upgrade head`.
6. Проверить, что `alembic check` не видит расхождений.
