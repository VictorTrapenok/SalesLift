# Тестирование и отладка

## Быстрый старт

```bash
make test              # unit-тесты — без БД, доли секунды
make test-integration  # интеграционные — поднимут PostgreSQL в Docker и погасят её после
```

Один файл или один тест:

```bash
cd packages/api
uv run --env-file .env.test pytest tests/integration/test_auth_service.py
uv run --env-file .env.test pytest -k "логин_с_неверным_паролем"
```

> ⚠️ **Всегда через `make` либо с `--env-file .env.test`.** Тесты делают
> `TRUNCATE`. Без этого флага настройки укажут на **базу разработки** (порт
> 5432), и данные, с которыми вы работаете руками, будут стёрты. `conftest.py`
> откажется стартовать, если `APP_ENV != test`, — но полагаться на предохранитель
> вместо привычки не стоит.

## Два яруса

Плюс третий, внешний, ярус — браузерные e2e на Playwright ([e2e/](../e2e/)):
они бьют не по коду, а по запущенному продукту через интерфейс, и живут на
воротах CI перед публикацией образа. Ниже — про два ближних яруса,
запускаемых из `packages/api`; про e2e см. [e2e/README.md](../e2e/README.md).

### Unit — без БД

`packages/api/tests/unit/`

| Файл                  | Что проверяет                                                    |
| --------------------- | ---------------------------------------------------------------- |
| `test_errors.py`      | Иерархия доменных ошибок, коды, `field`                           |
| `test_i18n.py`        | **Совпадение наборов ключей всех локалей**, `resolve_locale`      |
| `test_permissions.py` | Маппинг ролей, разворачивание прав, устойчивость к мусору из БД   |
| `test_schema.py`      | Конвенция именования резолверов, экспортируемость схемы, отсутствие `passwordHash` в контракте |

Не требуют ни Docker, ни PostgreSQL.

### Интеграционные — реальная PostgreSQL, без моков

`packages/api/tests/integration/`

| Файл                   | Что проверяет                                                     |
| ---------------------- | ----------------------------------------------------------------- |
| `test_db_harness.py`     | Мягкое удаление, глобальная уникальность e-mail, CHECK-ограничения |
| `test_auth_service.py`   | Регистрация, вход, гонка дубликата e-mail, отключённые аккаунты    |
| `test_users_service.py`  | Список сотрудников, заведение, смена роли/статуса, удаление, изоляция тенантов |
| `test_profile_service.py`| «О себе», язык, смена пароля с проверкой текущего                  |
| `test_tenant_service.py` | Настройки компании                                                |
| `test_graphql_api.py`    | Контракт ошибок и сквозные сценарии через HTTP                     |

**Никаких моков моделей.** Тест, проверяющий поведение против мока, проверяет
мок. Все интеграционные тесты работают на настоящей PostgreSQL той же версии,
что и в production.

`test_graphql_api.py` бьёт по приложению в процессе (`httpx` + `ASGITransport`),
без реального порта, но проходит весь путь: роутер → контекст → резолвер →
сервис → БД.

## Тестовая база

Отдельный одноразовый контейнер на **порту 5433** (разработка — 5432): полная
изоляция от базы, с которой вы работаете. Volume не подключается — база всегда
стартует с чистого листа.

```bash
make test-db-start   # поднять вручную
make test-db-stop    # погасить
```

Параметры — в `packages/api/.env.test` (файл коммитится: секретов там нет по
определению, а `make test-integration` должен работать сразу после клона).

## Модель изоляции

Устройство `tests/integration/conftest.py`:

| Фикстура       | Область   | Что делает                                            |
| -------------- | --------- | ----------------------------------------------------- |
| `db_engine`    | сессия    | Движок + `alembic upgrade head`. Один раз за прогон.   |
| `clean_db`     | модуль    | `TRUNCATE` перед каждым тестовым **файлом** (autouse). |
| `session`      | тест      | Сессия БД. Без обёртки в откатываемую транзакцию.      |
| `tenant`       | тест      | Компания для теста.                                    |
| `other_tenant` | тест      | **Вторая компания — для проверок изоляции.**           |
| `admin_user`   | тест      | Активный администратор компании `tenant`.              |

Три вещи, которые важно понимать:

**`TRUNCATE` перед модулем, а не перед каждым тестом.** Тесты внутри файла
опираются на данные, созданные ранее в этом же файле. Из этого следует, что
внутри модуля данные предыдущих тестов **живы** — если тест ищет запись по
неуникальному полю (например, по названию компании), он найдёт чужую. Поэтому
в таких проверках используйте уникальное значение: `f"Компания-{uuid4().hex[:8]}"`.

**Тест не оборачивается в откатываемую транзакцию.** Границами транзакций
управляет сервисный слой, и подменять их — значит проверять не тот код, который
поедет в production. Данные реально коммитятся, чистит их `clean_db`.

**Комбинация «TRUNCATE на модуль + тенант на тест» и делает осмысленными
проверки изоляции**: в базе есть реальные чужие данные, которые запрос может
утечь.

### Единый TRUNCATE — не трогать

```python
await conn.execute(text(f'TRUNCATE TABLE {tables} CASCADE'))
```

Одним statement'ом, а не циклом по таблицам: PostgreSQL берёт
AccessExclusive-локи на все перечисленные таблицы **атомарно**, поэтому
конкурентные вызовы не могут заблокировать друг друга. Сейчас, при однопоточном
pytest, гонок нет — но так просто быстрее (один запрос вместо N), а защита от
дедлоков уже на месте. В прототипе до перехода на единый statement тесты падали
с `deadlock detected`.

### ⚠️ Не добавляйте pytest-xdist

pytest однопоточен по умолчанию, и это здесь **свойство, а не ограничение**: все
интеграционные тесты делят одну тестовую базу. Параллельный прогон вернёт гонки
на миграциях и дедлоки на `TRUNCATE` — ровно те, которые прототип уже чинил.

Если тесты станут медленными, ускоряйте их, а не распараллеливайте.

## Принципы

1. **Без моков.** Реальная PostgreSQL, реальное поведение.
2. **Проверяем тип доменной ошибки**, а не текст сообщения: текст зависит от
   локали и меняется, тип — контракт.
   ```python
   with pytest.raises(ValidationError) as err:
       await auth_service.register(session, data, "ru")
   assert err.value.field == "email"
   ```
3. **Имена тестов — по-русски.** Имя теста читают в отчёте о падении, и
   `test_несуществующий_email_даёт_ту_же_ошибку_что_неверный_пароль` объясняет
   проблему без открытия файла. PEP 3131 это разрешает; ruff `N802` для
   `tests/**` отключён в `pyproject.toml`.
4. **Тест объясняет, зачем он есть.** Docstring отвечает на «что сломается, если
   это перестанет работать», а не пересказывает код.
5. **У каждого tenant-scoped сервиса обязателен тест «не видит чужой тенант».**
   Изоляция держится на дисциплине (явный `.where(tenant_id == ...)`), а не на
   магии ORM — значит, единственная её гарантия это тесты.

## Как написать тест для нового сервиса

```python
"""Интеграционные проверки <сервиса>. Реальная PostgreSQL, без моков."""

import uuid

import pytest
from sqlalchemy.ext.asyncio import AsyncSession

from saleslift.models import Tenant
from saleslift.services.<domain>.<entity>_service import entity_service
from saleslift.utils.errors import NotFoundError


class TestCreate:
    """Создание сущности."""

    async def test_создаёт_и_привязывает_к_компании(
        self, session: AsyncSession, tenant: Tenant
    ) -> None:
        result = await entity_service.create(session, {...}, tenant.id, "ru")

        assert result.tenant_id == tenant.id

    async def test_не_видит_данные_чужого_тенанта(
        self, session: AsyncSession, tenant: Tenant, other_tenant: Tenant
    ) -> None:
        """Обязательный тест для любого tenant-scoped сервиса."""
        created = await entity_service.create(session, {...}, other_tenant.id, "ru")

        with pytest.raises(NotFoundError):
            await entity_service.get(session, created.id, tenant.id, "ru")
```

Фикстуры подключать не нужно: `conftest.py` в `tests/integration/` даёт их
всем тестам каталога.

## Отладка

**Состояние тестовой базы** после упавшего теста — контейнер гасится в конце
прогона, поэтому смотреть надо, пока он жив:

```bash
make test-db-start
cd packages/api && uv run --env-file .env.test pytest tests/integration/test_auth_service.py
docker exec -it saleslift-test-db psql -U saleslift_test -d saleslift_test -c "SELECT * FROM users"
make test-db-stop
```

**База разработки:**

```bash
docker compose exec db psql -U saleslift -d saleslift -c "\d users"
```

**Логи** в разработке человекочитаемые, в тестах и production — JSON
(`LOG_LEVEL=debug` для подробностей). Для CI задаётся `LOG_FILE_PATH`: файл
монтируется наружу и прикладывается артефактом к прогону — именно это делает
красный билд отлаживаемым.

## Когда появится отправка писем

Сейчас `MailService` нет: администратор задаёт пароль сотруднику напрямую,
приглашений и подтверждений e-mail не существует.

Когда появятся, **не мокайте отправку**. Рабочий паттерн из прототипа: под
`APP_ENV=test` сервис писем не вызывает внешний API, но пишет строку в таблицу
`sent_emails` со `status='sent'` — как и в production. Тесты проверяют по этой
таблице, какое письмо ушло, кому и с какими переменными. Секреты (токены
сброса, приглашения) в журнал не пишутся, и тест обязан это проверять.

Это тестирует реальный путь кода, а не то, что мок был вызван.
