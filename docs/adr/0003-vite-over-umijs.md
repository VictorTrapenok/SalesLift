# ADR-0003. Vite вместо UmiJS Max

**Статус:** принято

## Контекст

Фронтенд прототипа построен на **UmiJS Max** — фреймворке поверх React,
приносящем разом роутинг, layout, `access` (права), `locale` (i18n), `model`
(состояние) и `request`. Прототип использовал их все.

Новый фронтенд — SPA на React + Ant Design + Apollo с пятью страницами.
Вопрос: брать UmiJS Max, чтобы переиспользовать решения прототипа, или собрать
на Vite явно.

## Решение

**Vite + React 19 + react-router 7 + i18next.** ProLayout из
`@ant-design/pro-components` берём — он отделим от фреймворка и работает под
Vite как обычный npm-пакет.

## Обоснование

**Главная ценность UmiJS отделима.** Самое полезное в нём — ProLayout, и он
доступен отдельным пакетом. Забираем его, фреймворк не берём.

**Остаток — примерно 200 строк явного кода.** `access` + `locale` + `model` +
`request` для пяти страниц это `<ProtectedRoute>`, инициализация i18next, хук
`useCurrentUser` и Apollo-клиент, который мы всё равно пишем. Для кодовой базы,
чья заявленная цель — архитектурная ясность, «проводку авторизации видно в
одном файле» лучше, чем «настроено в `.umirc.ts` и сгенерировано в `src/.umi/`».

**Скорость сборки.** `web-builder` — самый медленный стейдж Dockerfile. На путь
пользователя это не влияет (он тянет готовый образ), но напрямую влияет на
длительность каждого прогона CI. UmiJS добавляет `max setup` в postinstall и
собирает заметно дольше.

**Генерируемый код внутри исходников.** UmiJS создаёт `src/.umi/` и
`src/.umi-production/` — около шестнадцати директорий прямо в дереве
исходников, которые приходится держать в `.gitignore`. Вывод Vite остаётся в
`dist/` и `node_modules/.vite`.

## Контраргумент, который отвергаем

Конвенциональный роутинг UmiJS и его плагин `locale` — это меньше кода, чем
react-router + i18next. Примерно на тридцать строк.

Не стоит фреймворка, чей жизненный цикл плагинов нужно изучать отдельно, а
документация наполовину на китайском. Тридцать строк явного кода читаются, а
поведение плагина — выясняется.

## Чем заплатили

- **Роутинг описывается вручную** в `router.tsx` вместо вывода из структуры
  файлов. При двадцати страницах это начнёт раздражать; при пяти — нет.
- **Нет `useModel`** — глобального состояния из коробки. Пока не нужно: профиль
  пользователя кэширует Apollo, остальное локально в компонентах. Понадобится —
  берём Zustand.
- **Решения прототипа не переносятся копированием.** Пришлось переписать
  `access.ts` в `<ProtectedRoute>` + `HasPermission`, а `getInitialState` — в
  `useCurrentUser`. Логика та же, форма другая.

## Что перенесли из прототипа как есть

- Структура страницы: `index.tsx` (оркестрация) + `queries.ts` (все `gql`) +
  `components/`.
- Конфигурация codegen: чтение SDL-файла, сканирование `gql` в компонентах.
- Звенья Apollo: `errorLink` → `authLink` → `httpLink`, включая защиту от
  гонки токенов через `requestedWithToken`.
- Локали как TS-модули (не JSON) — ради проверки согласованности компилятором.
- `data-qa` атрибуты в вёрстке.
- Брендинг через `constants/brand.ts`.
