# ADR-0001. Резолвинг тенанта без поддоменов

**Статус:** принято

## Контекст

Мультитенантный SaaS должен на каждом запросе понимать, к какой компании
относятся данные. Прототип (`proto-saas`) решал это поддоменами:
`company.example.com` → slug `company` → тенант из БД. E-mail был уникален
только внутри тенанта (`UNIQUE (tenant_id, email)`), поэтому один человек мог
иметь независимые аккаунты в разных компаниях.

Требование к новому проекту: **все кабинеты на одном домене, без поддоменов**.
Значит, механизм прототипа неприменим целиком, а не частично.

## Решение

**E-mail глобально уникален. Компания выводится из строки пользователя.**

```sql
CREATE UNIQUE INDEX uq_users_email ON users (email) WHERE deleted_at IS NULL;
```

- Форма входа содержит только e-mail и пароль. Поля «компания» нет.
- Поиск пользователя по e-mail **и есть** резолвинг тенанта: `tenant_id`
  читается со строки найденного пользователя.
- JWT несёт `{user_id, tenant_id}`.
- У тенанта нет slug'а: единственный идентификатор — `id` (UUID).

Индекс **частичный** (`WHERE deleted_at IS NULL`): записи мягко удалённых
сотрудников остаются в таблице, и без этого условия адрес уволенного был бы
занят навсегда.

## Чем заплатили

**Один человек не может работать в двух компаниях под одним адресом.** В
прототипе это было возможно и специально поддерживалось: логин на
auth-поддомене перебирал кандидатов по совпавшему паролю, а Google OAuth при
e-mail в нескольких тенантах отдавал список организаций с предподписанными JWT.

Мы этот сценарий теряем. Обходной путь для пользователя — почтовые алиасы
(`ivan+acme@example.com`). Если сценарий станет востребованным, потребуется
вводить выбор компании в форме входа — то есть менять и схему, и UX.

**Slug'а нет — в логах и ключах хранилища стоит UUID**, а не читаемое имя.
Чтобы понять, чья это компания, нужен запрос в БД. Приемлемо; если начнёт
мешать, можно добавить неуникальный `display_slug` чисто для косметики, не
трогая идентичность.

## Что это дало

- **`build_context` сжался со ~150 строк до ~40.** Исчезли: резолвинг
  поддомена, сверка поддомена с токеном, `DEV_TENANT_NAME` для локальной
  разработки, заголовок-обход для e2e, `forceAdminTenant` для админки.
- **Из формы регистрации исчезло поле «придумайте адрес»** вместе с
  транслитом, валидацией и разрешением коллизий slug'ов.
- **Названия компаний не обязаны быть уникальными** — две «Ромашки» не мешают
  друг другу.
- **DNS настраивать не нужно.** Ни wildcard-записи, ни wildcard-сертификата.

## Что осталось от прототипа

Сверка `tenant_id` из токена с БД в `build_context` — единственная проверка
целостности, пережившая отказ от поддоменов. Штатно сработать не может; если
сработала — токен подделан или пользователя перенесли между компаниями.

## Альтернативы

**Slug компании в форме входа** (`UNIQUE (tenant_id, email)`, как в прототипе).
Сохранял бы работу в нескольких компаниях и модель данных прототипа. Отвергнуто:
лишнее поле в форме, которое пользователь должен помнить, ради сценария,
которого у нас пока нет.

**Slug в пути URL** (`/t/acme/employees`). Тенант виден в адресе, форма входа
остаётся короткой. Отвергнуто: усложняет роутинг и все ссылки в приложении,
а выигрыша по сравнению с выводом тенанта из e-mail не даёт.
