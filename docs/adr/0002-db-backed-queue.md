# ADR-0002. Очередь фоновых задач в PostgreSQL

**Статус:** принято

## Контекст

Аналитика звонков требует фоновой обработки: транскрибация и анализ идут
минутами и не помещаются в HTTP-запрос. Нужна очередь.

Стандартный ответ в Python-экосистеме — Celery + Redis. Но у проекта есть
жёсткое требование к упаковке: **клиент разворачивает продукт одной командой**,
имея только Docker. Каждая дополнительная stateful-зависимость — это ещё один
сервис в compose, ещё один под в Helm-чарте и ещё одна причина, по которой
установка не заведётся с первого раза.

## Решение

**Очередь живёт в PostgreSQL**, которая и так есть. Таблица `background_tasks`,
захват задачи через `FOR UPDATE SKIP LOCKED`:

```sql
UPDATE background_tasks SET status='running', worker_id=:worker_id, locked_at=now()
WHERE id IN (
  SELECT id FROM background_tasks
  WHERE status='pending' AND deleted_at IS NULL
  ORDER BY created_at
  FOR UPDATE SKIP LOCKED
  LIMIT :limit
)
RETURNING *;
```

`SKIP LOCKED` позволяет нескольким воркерам разбирать очередь параллельно, не
блокируя друг друга и не рискуя взять одну задачу дважды.

Воркер — тот же образ с `APP_MODE=worker`.

## Чем заплатили

- **Нет fan-out.** Одна задача — один исполнитель. Публикация события многим
  подписчикам потребует другого механизма.
- **Задержка — секунды, а не миллисекунды.** Воркер опрашивает таблицу; между
  постановкой и началом работы проходит интервал опроса. Для транскрибации,
  которая идёт минуты, это неразличимо. Для интерактивных сценариев — нет.
- **Нагрузка на ту же БД**, что обслуживает запросы. При тысячах задач в
  секунду опрос начнёт мешать. Мы очень далеко от этого масштаба.
- **Своего кода больше**, чем при Celery: планировщик, захват, восстановление
  зависших задач пишем сами (~200 строк вместо конфигурации).

## Что это дало

- **Ни одной новой зависимости.** `helm install` на голом k3s поднимает
  работающий продукт; в compose — два сервиса вместо четырёх.
- **Транзакционность бесплатно.** Задачу можно поставить в той же транзакции,
  что и изменение данных: либо оба, либо ничего. С Redis это отдельная забота
  (задача уже в очереди, а транзакция откатилась).
- **Отладка обычным SQL.** `SELECT * FROM background_tasks WHERE status='failed'`
  вместо инструментов инспекции Redis.
- **Состояние задач переживает перезапуск** без настройки персистентности.

## Когда пересматривать

Сигналы, что решение перестало подходить:

- задержка старта задач стала заметна пользователю;
- понадобился fan-out или приоритеты сложнее `ORDER BY created_at`;
- опрос очереди виден в профиле нагрузки на БД.

Тогда — ARQ (asyncio-native, легче Celery) либо Celery, если понадобится его
экосистема. Миграция затронет `services/tasks/` и `jobs/`, но не доменный код:
задачи ставятся через сервис, а не напрямую в очередь.

## Семантика доставки

**At-least-once.** Воркер может умереть после выполнения работы, но до отметки
`done` — тогда задача выполнится повторно. **Обработчики обязаны быть
идемпотентны.**

Зависшие задачи (в `running` дольше 10 минут) возвращает в `pending` джоб
`stale_task_recovery`, инкрементируя `attempt_number`.

## Альтернативы

**Celery + Redis.** Индустриальный стандарт, узнаваем. Отвергнуто: Redis
становится обязательной зависимостью установки ради возможностей, которые нам
не нужны.

**ARQ + Redis.** Легче Celery, asyncio-native, хорошо ложится на FastAPI. Тот
же минус: Redis.
