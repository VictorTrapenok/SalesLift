# CLAUDE.md

## Архитектурные принципы и стиль

- Мы делаем B2B SaaS с низкой посещаемостью. **Читаемость кода и простота
  поддержки важнее производительности.**
- Комментарии и документация — **на русском языке**. Комментарий к функции,
  методу или атрибуту класса должен быть документирующим: docstring `"""..."""`
  в Python, JSDoc `/** ... */` в TypeScript.
- **Резолверы GraphQL** называются `resolver_<резолвер>_<метод>`:
  `resolver_auth_register`, `resolver_auth_login`. Strawberry применяет
  camelCase, поэтому в схеме получается `resolverAuthRegister` — префикс
  переживает преобразование, и резолвер грепается с обеих сторон
  (`rg resolver_auth` в Python, `rg resolverAuth` в TypeScript). Конвенцию
  проверяет `tests/unit/test_schema.py`.
- На фронтенде в вёрстку добавляй **`data-qa`** атрибуты со значениями, по
  которым понятно назначение элемента и легко найти отвечающий за него код.
  Значения могут содержать переменные, но всегда начинаются со статичного
  префикса.
- Файлы **больше 500 строк** дроби на части. На фронтенде — на компоненты.
- **Строгая типизация везде.** `mypy --strict` на бэкенде, `strict` в
  `tsconfig.json` на фронтенде. Обе проверки в CI, обе обязаны быть зелёными.
- **Всегда указывай явный тип возвращаемого значения** у всех функций, методов
  и стрелочных функций — включая резолверы, обработчики и колбэки. Не
  полагайся на вывод типов.
- **Каждый `except` / `catch` логирует ошибку.** Пустой `except: pass`,
  `.catch(() => {})` запрещены — они превращают отладку в гадание. Если ошибку
  действительно можно проигнорировать, комментарием поясни почему.
- **Избегай fire-and-forget** — он сильно осложняет тестирование.
- **Все импорты в начале файла.** Никаких импортов внутри функций и методов.
- **Избегай N+1.** В GraphQL предпочтительнее специализированный резолвер,
  тянущий данные одним запросом с join, чем ленивая подгрузка по элементу.
  Связи в моделях объявлены с `lazy="raise"`: забытый `selectinload` упадёт
  явной ошибкой, а не тихо превратится в N запросов.
- **i18n-ключи используются как полная строка-литерал**, а не собираются из
  фрагментов: `t('auth.login.title')`, но не `t(f'auth.{page}.title')`.
  Собранный ключ невозможно найти грепом, и его теряют при рефакторинге.
- **Бизнес-логика — в сервисах, а не в резолверах.** Резолвер это тонкий
  адаптер: разобрал вход → позвал сервис → собрал ответ. Сервисы —
  объектно-ориентированные, экспортируются синглтоном, DI-контейнера нет.
- **Брендинг — через константы**, а не хардкодом: `config/constants.py` на
  бэкенде, `constants/brand.ts` на фронтенде. Имя продукта, домен и прочее
  берутся оттуда.
- Мы **на стадии до MVP**, поэтому не заботимся об обратной совместимости API.
  Это НЕ относится к схеме БД: миграции обязаны быть совместимы с предыдущей
  версией кода на один релиз — см.
  [migrations/readme.md](packages/api/src/saleslift/migrations/readme.md).
- Все шероховатости недоработки всё остальное Фиксируй в файле ROADMAP.md

Подробная архитектура — [ARCHITECTURE.md](ARCHITECTURE.md), тестирование —
[docs/testing.md](docs/testing.md), рабочее окружение —
[docs/development.md](docs/development.md).

## Порядок обновления документации

`CLAUDE.md` и `ARCHITECTURE.md` содержат **общие базовые принципы** и играют
роль оглавления и глоссария. Детали живут в отдельных `.md` файлах **рядом с
кодом**, который они описывают, а корневые документы на них ссылаются. Так
корневые файлы не разбухают и остаются актуальными.

Если изменение в коде требует обновления документации:

1. Определи, что нужно обновить: `CLAUDE.md`, `ARCHITECTURE.md` или отдельный файл.
2. Внеси изменения в код и протестируй их.
3. Обнови документацию; при необходимости добавь ссылку на новый файл в
   `CLAUDE.md` / `ARCHITECTURE.md`.
4. Убедись, что документация соответствует текущему состоянию кода.

- **Документацию клади рядом с кодом**, в той же папке.
- **Примеры вызовов в документации устаревают.** В `.md` оставляй названия
  функций и общее назначение; списки аргументов и примеры — в документирующем
  комментарии в коде.
- Новые термины поясняй в разделе «Глоссарий» в [ARCHITECTURE.md](ARCHITECTURE.md).
- **Не документируй то, чего нет.** Инструкция, которая не запускается, хуже
  отсутствующей.

## Commands

Полный список — `make` без аргументов. Ниже только неочевидное.

```bash
# Схема бэкенда → TypeScript-типы фронтенда. ОБЯЗАТЕЛЬНО после правки схемы.
make codegen

# Unit-тесты (без БД) и интеграционные (поднимут PostgreSQL в Docker на 5433)
make test
make test-integration

# Один тестовый файл
cd packages/api && uv run --env-file .env.test pytest tests/integration/test_auth_service.py

# Порт 8000 занят
make dev-api PORT=8081
make dev-web PORT=8081
```

**Тесты запускать только через `make`** либо с `--env-file .env.test`: они
делают `TRUNCATE`, и без этого флага настройки укажут на базу разработки.
`conftest.py` откажется работать, если `APP_ENV != test`.

## Architecture

- Python **3.13**, Node **24**, PostgreSQL **18**.
- Пакетный менеджер Python — **uv**. Он же ставит интерпретатор.

| Пакет          | Что                                                    |
| -------------- | ------------------------------------------------------ |
| `packages/api` | Бэкенд: FastAPI + Strawberry GraphQL + SQLAlchemy 2.0  |
| `packages/web` | Фронтенд: Vite + React 19 + Ant Design + Apollo Client |

### Data Model

```
Tenant (1) ──→ User (many)              permissions: admin | manager | viewer
Tenant (1) ──→ BackgroundTask (many)
```

Все таблицы: UUID PK, мягкое удаление (`deleted_at`), `created_at`/`updated_at`.

## Руководство по ревью

Используй `gh`.

Проверяй логичность именования компонентов, функций, переменных и файлов.
Цель ревью:

- сохранять код читаемым и поддерживаемым;
- предотвращать архитектурный хаос;
- снижать риск багов;
- удерживать единый стиль проекта.

Приоритеты, по убыванию:

1. **Простота.** Не переусложнено ли решение? До MVP простое предпочтительнее.
2. **Понятность.**
3. **Консистентность.** Изменения не должны ломать существующее поведение.
4. **Безопасность изменений**: типизация, валидация, лишние запросы, N+1,
   корректность работы с БД.

Отдельно смотри:

- **Изоляция тенантов.** У каждого запроса к данным есть явный
  `.where(Model.tenant_id == tenant_id)`? Есть ли тест «не видит чужой тенант»?
- **Обратная совместимость миграций** (см. правило expand-contract).
- **`schema.graphql` перегенерирован**, если менялись резолверы?
